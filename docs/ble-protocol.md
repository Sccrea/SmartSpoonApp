# 智味勺 · 蓝牙（BLE）对接说明

这份文档是**勺子固件**（`C:\Users\Administrator\Desktop\t8\t8.ino`）与**安卓应用**
（`android/app/src/main/java/com/smartspoon/l2/SpoonProtocol.kt`）之间唯一的约定。
两边任何一方改协议，都必须同时更新这份文档 —— 它是排查"连上了但读数是 0 / 按键没反应"
这类问题的第一手依据。

```
勺子（Arduino Nano 33 BLE Sense）          手机（Gramo App）
   HX711  重量 ─┐
   LSM6DS3 姿态 ─┼─► 状态帧 S,...
   D3 握持传感  ─┤      每 100ms           ┌─►「用餐中」实时读数
   BodySense 记口┘   事件帧 B,...          │
                        │                 │
                   NUS Notify 6E400003 ───┘
                   NUS Write  6E400002 ◄───┴── ZERO / MODE / PING / VER?
                                                （归零、切模式、探活、读版本）
```

## 1. 传输层：Nordic UART Service（NUS）

用的是 Adafruit nRF52 板级包里 `BLEUart` 自带的那套 UUID，**不需要自己编 UUID**：

| 用途 | UUID | 方向 |
| --- | --- | --- |
| 服务 | `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` | — |
| 通知（Notify） | `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` | 勺子 → 手机 |
| 写入（Write） | `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` | 手机 → 勺子 |

- 广播名：**`SmartSpoon`**（`Bluefruit.setName("SmartSpoon")`）。
- 手机端扫描**不按服务 UUID 做硬件过滤**，原因是广播包只有 31 字节，128 位 UUID
  经常放不进去 —— 硬件过滤会导致"一条回调都不来"，现场表现就是怎么扫都扫不到。
  App 收所有广播，再按「服务 UUID 出现过」或「名字像勺子」自己筛。
- 连接成功后手机端订阅 Notify（写 CCCD），然后客户端 `tare/去皮` 由命令控制。

## 2. 上行：勺子 → 手机

每条消息以 `\n` 结尾（`bleuart.println`），字段用 `,` 分隔，**纯 ASCII**。
选文本而不是二进制的理由很实际：现场用 `nRF Connect` 或串口助手看到的就是同一批字符，
出问题时不需要任何翻译工具，一眼能分清是传感器坏了还是蓝牙断了。

### 2.1 状态帧（每 100ms 一条）

```
S,<weight10>,<body>,<stable>,<mark>[,<battery>]
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `S` | 字面量 | 帧类型 = 状态帧 |
| `weight10` | int | 勺中读数 **×10**（`123` = 12.3 g；可能是负数，未去皮时） |
| `body` | int 0~4095 | 握持/人体传感的 12 位 ADC 均值（诊断用） |
| `stable` | `1` / `0` | IMU 判定"端稳了"（加速度模长≈1g 且角速度 < 15 dps） |
| `mark` | int，单调递增 | 开机以来的累计**口数**，由 BodySense 自动记口时加一（固件 1.2 起；1.1 及以前是"按一次 SW3 加一"） |
| `battery` | int 0~100，**可省略** | 电量。没有电池检测时固定报 `100` |

**`battery` 是可选字段**：老固件只有前 5 个字段，手机端解析时会按 `-1` 处理，
不会因为少一个字段就丢整帧。追加新字段同理 —— 老 App 忽略多余字段。

### 2.2 事件帧

```
B,<mark>[,<weight10>]      自动记下"一口"（BodySense 判定嘴离开且勺子稳了）
                           weight10 = **这一口的净重** = 吃前重量 − 吃后重量（见「这一口多少克」一节）
                           固件 1.1 及以前：按 SW3 触发，weight10 报"本轮舀取的最大读数"
A,<key>,<value>            命令应答：A,APP,1 / A,VER,1.2 / A,ZERO,1 / A,MODE,1
E,<code>,<text>            出错，例如 E,CMD,unknown command
```

### 2.3 `mark` 的语义（最容易搞错的一处）

`mark` 是**开机以来的累计值**，不是"这一餐吃了几口"。
手机端自己用两次读数相减，得到"这一餐的第几口"。

这么设计的好处是：手机端**丢包、断线重连、换页面**都不会把同一口记两遍 ——
只要记住"上次见到的最大值"，比它大的才是新的一口。
固件同时也主动推 `B` 事件帧，两条路互为兜底（`SpoonLink` 内部去重，只会回调一次）。

## 3. 下行：手机 → 勺子

ASCII 命令，手机端发送时会自动补 `\n`；固件对 `\r\n` 也容忍（方便用串口助手手敲）。

| 命令 | 作用 | 应答 |
| --- | --- | --- |
| `ZERO` / `TARE` | 重量归零（重新 `tare(20)`） | `A,ZERO,1` |
| `MODE <0-2>` | 切换工作模式（0 打印串口 / 1 只发蓝牙 / 2 静默） | `A,MODE,<n>` |
| `PING` | 探活（App 连上后第一件事） | `A,APP,1` |
| `VER?` | 读固件版本 | `A,VER,<版本>` |

### 归零为什么要"两边各做一次"

App 里点「点击归零重量」时会：

1. 立刻把界面的勺中读数清 0（用户马上看到反馈）；
2. 同时下发 `ZERO` 让固件重新 `tare()`。

只做第 1 步的话，**100ms 后的下一个状态帧就会把旧读数顶回来** ——
这正是"点了归零，数字弹回原样"的经典原因。

### "这一口多少克"是谁说了算

这是实测才暴露出来的一个坑，值得写清楚：

**固件 1.1 及以前**：`B` 事件帧由 `SW3` 触发，而按 SW3 时勺子往往**已经空了**
（放进嘴里、或放下勺子时才按键），那一刻状态帧里的读数就是 `0`。
如果直接拿当前读数当这一口的重量，只会得到一条 **0 g 的假记录**。
所以那时固件报的是"本轮舀取的最大读数"（`t8.ino` 的 `peakWeight10`）。

**固件 1.2 起**：记口改由 BodySense 自动完成，重量按**吃前 − 吃后**算出净重，直接报在 `B` 帧里
（细节见第 6 节）。这比"峰值"更接近真实入口量：它减掉了勺子上没吃掉的那部分。

手机侧的两级兜底**保留着**（用于老固件、或 `B` 帧丢包的情况）：
`SpoonLink.emitBite` → `MealSession.onSpoonBite`：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `B,<mark>,<weight10>` 里的重量 | 固件报的净重（1.2+）或本轮峰值（≤1.1），最准 |
| 2 | App 侧"最近一次非零读数" | 老固件不带重量字段时的兜底（`SpoonLink.peakWeight10`） |
| 3 | App 侧"本轮舀取的最大读数" | 状态帧与 `B` 帧错开时的兜底（`MealSession.peakSpoonWeight`） |

三级都是 0 才拒绝记这一口，并明确提示"没有读到重量"，而不是静默吞掉或编一个 15 g。

> 固件 1.2 里，**出厂的"峰值"逻辑已经删掉**（`peakWeight10` 不复存在）：
> 净重是算出来的，不需要再去猜一个峰值。归零（`ZERO`/`TARE`）仍然会清掉滤波器与读数。

## 4. App 侧的对应实现

| 文件 | 职责 |
| --- | --- |
| `SpoonProtocol.kt` | UUID、帧格式、解析（`parseLine` / `parseStatus`） |
| `FrameReader.kt` | 把 Notify 的字节流按 `\n` 切帧（半包/粘包重组，`SpoonLink` 与自测共用） |
| `SpoonLink.kt` | 扫描 / 连接 / 打开 Notify / 命令下发 / 自动重连 / stale 看门狗 / 口数去重 |
| `BleSpoon.kt` | 把解析后的数据落到 `State` / `MealSession`，并把设备补进设备列表 |
| `BlePermissions.kt` + `BlePermissionActivity.kt` | 蓝牙运行时权限（12+ 用 `BLUETOOTH_SCAN/CONNECT`，11- 用定位；弹窗没法申请权限，走透明中转页） |
| `SpoonSelfTest.kt` | 自测数据源：造真帧、故意切成半包，走与真机完全相同的解析路径 |

`SpoonLink` 是应用级单例（`object`），连接与任何 Activity 的生死无关 ——
否则"设备管理页连上 → 进「用餐中」又说未连接"。

## 5. 现场排查清单

排查第一步永远是看日志（应用把所有关键节点都打出来了）：

```powershell
adb logcat -s SpoonLink:V BleSpoon:V BlePermission:V
```

它会按顺序告诉你：适配器有没有、权限给没给、扫描有没有真的开始、扫到哪些候选设备
（含 MAC / 名字 / RSSI）、GATT 每一步的状态码。

| 现象 | 先看这里 |
| --- | --- |
| 扫不到勺子 | 勺子是否上电（固件启动 3 秒内会在 `Serial` 打印 `IMU OK` / `HX711 OK`）；手机蓝牙是否打开；Android 12+ 是否给了「附近的设备」权限；**定位开关是否打开**（见下） |
| **扫描报"错误码 1"** | 1 = `SCAN_FAILED_ALREADY_STARTED`，**不是真失败**：上一次扫描还在跑。App 现在把 `startScan` 做成幂等的（先停旧的再起新的），并且会忽略这个错误码 —— 如果你还看到它，说明用的是旧 APK |
| 点了「扫描」一直转圈、什么都不出来 | 看日志里有没有"开始扫描"。没有 = 被前置检查拦下了（蓝牙没开 / 没权限 / 定位关着），界面上的提示会写明是哪一条 |
| 扫到但连不上（GATT 133） | 勺子是否已被别的手机连着（BLE 外设通常只接受 1 个中心设备）；关掉别的连接再重试。日志里 `onConnectionStateChange state=… status=133` 就是它 |
| 手机设置里能看到 SmartSpoon，但 App 扫不到 | 手机设置页走的是**经典蓝牙/系统级扫描**，与 BLE 扫描是两条路。App 扫不到而设置页能看到，几乎总是"定位开关关着"或"扫描被前置检查拦下"——先看上面那条日志 |
| 连上但读数一直 0 | 是否 `tare` 过了；HX711 的 `DOUT/SCK` 接线；`CALIBRATION_FACTOR` 是否与你的实测一致（见固件顶部注释） |
| 读数跳动很大 | HX711 供电/接地；`scale.get_units(5)` 的采样数；秤体机械结构是否有应力 |
| 手机不记口（自动记口失效） | 先看串口：有没有打印过 `BASELINE <值>`（没打印 = 那 2 秒还没跑完、或串口没开）；再看嘴接触时有没有 `MOUTH ON pre=…`。出现 `BITE IGNORED` = 判定到了但净重 ≤ 0.5 g（空勺/手抖）；两行都看不到 = `BASELINE` 标定被抬高了（那 2 秒里把勺子叼在嘴里了），重启一次即可重标 |
| 连上就没数据（3 秒后提示休眠） | 固件是否处于 `MODE 2`（静默，不推状态帧）；或距离过远 |

### 关于"定位开关"

Android 12+ 有了 `BLUETOOTH_SCAN`（且声明了 `neverForLocation`）之后**不再需要定位权限**，
但不少 ROM（尤其国内定制系统）仍然要求**系统定位开关是打开的**，否则扫描既不报错、
也不回调任何结果 —— 现场表现就是"一直转圈，什么都没扫到"。

App 现在会主动查一眼并给出明确提示，而不是让用户对着转圈猜。
如果你的手机就是这样，打开定位开关即可（不需要给 App 定位权限）。

### `mark` 的三道防线（不记口时先看这里）

`mark` 是口数去重的基准：**只记"比基准大的 mark"**。所以一个异常大的脏值会把门槛顶死 ——
真机上出现过 `mark` 解析成 **5100** 的帧，之后所有正常的 7、8、9… 全被判"已处理过"，
表现就是**串口 MARK 一直在涨、App 一口都不记，而且不会自愈**。

现在有三道防线：

| 防线 | 位置 | 作用 |
| --- | --- | --- |
| 1. 字段量程检查 | `SpoonProtocol.parseStatus` | weight/body/mark 超出物理可能范围的帧整帧丢弃（mark 上限 10 万） |
| 2. `B` 帧量程检查 | `SpoonLink.handleLine` | `B,<mark>` 里的 mark 超量程时丢帧并记日志 |
| 3. 基准自愈 | `SpoonLink.emitBite` | 比基准小**且差得离谱**（> 100）时判为"勺子重启 / 基准是脏数据"，重置基准重新同步 |

另外每一帧都打日志：`收到 B 事件帧` / `状态帧里 mark 增长` / `报出一口` / `口数去重`
/ `可疑状态帧（N 个字段，疑似粘帧）`。抓一次日志就能分清是"B 帧没到"还是"到了但被去重挡住"。

> 粘帧（两个数字粘成 `S,1255,970,1,7,5100,9100`）本身是 BLE 数据被挤在一起造成的，
> 属于**链路层**问题。上面的防线保证它不会再把口数功能卡死；把连接参数收紧
> （固件里的 `setConnInterval(12, 24)` / 从机延迟 0）能显著减少这种情况。

## 6. 固件 1.2：按键与自动记口

固件源码在 `Desktop\firmware\firmware.ino`（1.2 起从 `t8.ino` 独立出来）。

### 6.1 三个按键

| 按键 | 引脚 | 功能 |
| --- | --- | --- |
| SW1 | D9 | **去皮 / 归零** —— 与手机端 `ZERO` 命令同一条路径 |
| SW2 | D8 | **电源键**：长按 2 秒 → **松开时**关机（System OFF，再按一下唤醒）；**双击** → 软件重启（`NVIC_SystemReset`）；单击不做任何事 |
| SW3 | D7 | **空闲**（保留引脚定义，`pinMode` 与读取都已去掉） |

- 关机前会依次停广播、`scale.power_down()`、拉低 `BODY_DRIVE`、关掉 IMU 的加速度计与陀螺仪、
  熄灭板载 LED —— 否则"关机"之后这些外设还在耗电。
- 唤醒条件是 **SW2 拉低**（`systemOff(SW2, LOW)`，SW2 是 `INPUT_PULLUP`，按下即低电平）。
- 双击重启与"开机"是**同一条路径**：都从复位向量重新跑 `setup()`，静态状态全部回到初值。
  所以"开机自动执行一次重置"不需要额外代码，只需要在 `setup()` 里重新标定 baseline。

### 6.2 自动记口的判定

```
开机 / 重启
   │  前 2 秒：对 BodySense 读数取平均 → baseline（这 2 秒内不判定接触）
   ▼
body > baseline + 50  ──► 【A 点】嘴正在接触
   │                        立刻记下"吃前重量" preWeight
   ▼
嘴离开（body 回落到 baseline 以下）且 IMU 判定端稳
   │
   ▼
【B 点】读"吃后重量" postWeight
净重 biteWeight = preWeight − postWeight
若 > 0.5 g：mark +1，推 B 帧（带净重 ×10）
```

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `BASELINE_MS` | 2000 | 开机后用于求 baseline 平均值的时长 |
| `BASELINE_OFFSET` | 50 | 超过 baseline 这么多即视为嘴接触 |
| `MIN_BITE_GRAMS` | 0.5 | 净重低于它视为噪声，**不记口**（只打串口日志） |
| `CHEW_TIMEOUT_MS` | 20000 | 嘴离开了但勺子一直不稳时的超时保护 |

两个判定细节（都是"反着做就不工作"的地方）：

- **A 点不要求稳定**：嘴接触那一刻手还在动，要求稳定就永远等不到；
- **B 点要求"嘴离开 **且** 稳定"**：只看嘴离开会抓到重量还在下落的中间值；
  只看稳定则勺子搁在桌上一直稳定，会在嘴还接触时就误判成吃完。

### 6.3 现场注意

- **baseline 那 2 秒别把勺子叼在嘴里**：baseline 会被抬高，之后真正的接触超不过阈值，
  表现就是"一直不记口"。重启一次即可重标。
- **净重为负或很小是正常的**：说明这一口没吃进多少（空勺、手抖、只喝了口汤），
  此时不记口是**刻意的**，避免噪声变成一条假记录。
- 串口日志里的关键字：`BASELINE <值>`（标定完成）、`MOUTH ON pre=…`（A 点）、
  `BITE #n pre=… post=… net=…`（记到一口）、`BITE IGNORED net=…`（净重太小被丢弃）、
  `POWER_OFF_ARMED` / `POWER_OFF`（长按预备/关机）、`RESET`（双击重启）。
